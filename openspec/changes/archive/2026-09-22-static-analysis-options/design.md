# Design

## Context

Сейчас анализатор документации строится вокруг одного значения `requestHandlerName`, которое задаётся в конструкторе `HandlerCollector` по умолчанию как `IRequestHandler`. Это работает в сценарии одного контракта, но не подходит для проектов, где один и тот же анализатор должен вызываться несколько раз с разными интерфейсами обработчиков.

См. proposal.md — Why.

## Goals / Non-Goals

**Goals:**
- сделать способ явной настройки контракта обработчика, используемого в анализе;
- сохранить поведение по умолчанию для текущих сценариев;
- избежать скрытого глобального состояния и уменьшить риск ошибок при повторном использовании анализатора.

**Non-Goals:**
- не вводить новую библиотеку или инфраструктуру для выбора интерфейса;
- не менять логику построения call graph, entity discovery или validation discovery;
- не расширять область анализа за пределы выбора контрактов обработчика запросов.

## Decisions

### Decision: pass analysis settings explicitly through `AnalysisOptions`
Вызов `AnalyzeAsync<T>` будет принимать объект настроек, например `AnalysisOptions` с полем `RequestHandlerName`. При вызове создаётся `HandlerCollector(compilation, options.RequestHandlerName)`. Это делает поведение явным и локальным для каждого анализа, а не скрытым в статическом состоянии.

**Why this over alternatives**
- проще поддерживать несколько вызовов в одном клиентском проекте;
- устраняется многопоточность/глобальное состояние как источник ошибок;
- сохраняется обратная совместимость за счёт значения по умолчанию `IRequestHandler`.

**Alternatives considered**
- передавать строку напрямую в `AnalyzeAsync<T>(string requestHandlerName)`;
- проводить автоматическое определение имени интерфейса из `T` через рефлексию;
- хранить текущее значение в статическом поле на уровне анализатора.

Первый вариант допустим, но менее расширяемый: при появлении новых параметров настройки API быстро разрастётся. Второй вариант хрупок, потому что `T` не является надёжным источником выбора контракта и зависит от конкретного сценария использования. Третий вариант нарушает локальность состояния и ухудшает повторный запуск анализа.

### Decision: keep default contract backward-compatible
Если `AnalysisOptions` не переданы, используется `IRequestHandler` как текущее поведение. Это сохраняет существующую семантику и не требует пересмотра текущих потребителей.

**Why this matters**
- минимизирует риск регрессий;
- позволяет постепенно перевести вызовы на явную настройку без изменения всех точек входа сразу.

## Risks / Trade-offs

- [Risk] Разные проекты могут использовать одинаковые короткие имена интерфейсов в разных пространствах имён → Mitigation: выбор делается явно через `RequestHandlerName`, а не через неявное сопоставление по имени без namespace.
- [Risk] Использование строкового имени интерфейса может приводить к опечаткам → Mitigation: валидация опций и документирование допустимого значения; при необходимости можно добавить сильный тип или enum в будущем.
- [Risk] Слишком широкий список поддерживаемых контрактов может усложнить логику фильтрации → Mitigation: оставить текущую проверку по generic-типу и длине аргументов без расширения на лишние шаблоны до необходимости.

## Migration Plan

1. Добавить `AnalysisOptions` в публичный API `DocumentationAnalyzer`.
2. Оставить `IRequestHandler` как значение по умолчанию.
3. Прокинуть `RequestHandlerName` в `HandlerCollector`.
4. Обновить все точки вызова, которые требуют нестандартного интерфейса, чтобы передавать явные параметры.
5. Проверить, что минимальный сценарий без параметров сохраняет старое поведение.

## Open Questions

Нет открытых вопросов, которые меняют спецификацию или выбор архитектуры. Остаётся технический вопрос о том, стоит ли в будущем заменить строковое имя на более строгий тип, но он не влияет на текущий подход.
