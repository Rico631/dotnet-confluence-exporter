# Proposal

## Why

Анализ документации обработчиков в текущем виде жёстко привязан к одному контракту `IRequestHandler` и не позволяет удобно переиспользовать один и тот же анализатор для разных моделей интерфейсов в разных проектах. При этом сценарий использования предполагает многократный вызов анализа для разных `RequestHandlerName` в одном клиентском проекте. Это создаёт риск глобального состояния, усложняет тестируемость и делает API менее явным.

## What Changes

- Сохраняется статический класс `DocumentationAnalyzer` как точка входа для вызова анализа.
- В `AnalyzeAsync<T>` добавляется параметр `AnalysisOptions`, который явно задаёт используемый контракт обработчика.
- `AnalysisOptions` передаётся в `HandlerCollector`, чтобы определить, какие интерфейсы считать обработчиками запросов.
- Параметр `RequestHandlerName` становится явным и локальным для конкретного анализа, а не скрытой настройкой глобального состояния.
- Сохраняется совместимость с текущим поведением по умолчанию: если опции не переданы, используется `IRequestHandler`.

## Capabilities

### New Capabilities
- `code-documentation-analysis`: поддержка явной настройки контракта обработчика при анализе документации для разных видов `RequestHandlerName`.

### Modified Capabilities
- пусто

## Impact

- `DocumentationAnalyzer`
- `HandlerCollector`
- вызовы анализа в других проектах, где требуется разный интерфейс обработчика запросов
- тесты и интеграционные сценарии, завязанные на распознавание обработчиков
