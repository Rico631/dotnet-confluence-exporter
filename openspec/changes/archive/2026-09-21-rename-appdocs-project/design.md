# Design

## Context

Мотивация изменения описана в `proposal.md` — Why. Текущее состояние и ограничения, определяющие подход:

- Инструмент — единственный вспомогательный проект решения `WebApp4.slnx`: `AppDocs/AppDocs.csproj` (`net10.0`, `OutputType=Exe`), с `ProjectReference` на `..\WebApp4\WebApp4.csproj`.
- В `AppDocs.csproj` не заданы `RootNamespace` и `AssemblyName`, поэтому оба значения неявно равны имени проекта `AppDocs`. В 29 файлах `.cs` найдено 41 вхождение корневого сегмента `AppDocs` (в объявлениях `namespace` и директивах `using`).
- Точка входа — `Program.cs` (top-level statements): `DocumentationAnalyzer.AnalyzeAsync<AddCartItem>()`, затем `HandlerDocumentationRenderer.Render(...)` и сериализация результата в JSON в консоль.
- `DocumentationAnalyzer` находит проект в решении по имени сборки **анализируемого** проекта (`typeof(T).Assembly`, то есть `WebApp4.Application`), а не по имени сборки инструмента, поэтому переименование инструмента не влияет на этот поиск.
- `HandlerDocumentationRenderer` формирует XHTML для Confluence; имена типов и пространств имён в выходные данные не выводятся, поэтому переименование namespace не отражается на результате рендера.
- В решении нет тестовых проектов; `.editorconfig` содержит единственное правило (`CS1591` = `silent`).
- `README.md` (одна строка) и `SKILL.md` используют имя репозитория `dotnet-confluence-exporter`; вхождений `AppDocs` в них нет.

## Goals / Non-Goals

**Goals:**

- Привести имя каталога, файла проекта, корневого namespace и имени сборки инструмента к имени, отражающему его назначение — выгрузку документации приложения в Confluence.
- Сохранить историю Git для перемещённых файлов.
- Не изменить поведение инструмента, состав зависимостей, набор пакетов и форматы вывода.

**Non-Goals:**

- Переименование решения `WebApp4.slnx` и прикладных проектов `WebApp4`, `WebApp4.Application`, `WebApp4.Shared`.
- Переименование внутренних пространств имён (`ApiDocumentGenerator`, `CodeDocumentation` и их подпространств) и типов, а также перемещение файлов внутри проекта.
- Введение `Directory.Build.props` или общих свойств сборки, добавление тестовых проектов, изменение целевого фреймворка и версий пакетов.
- Обратная совместимость со старым именем namespace и сборки: внешних потребителей нет.

## Decisions

### 1. Целевое имя проекта — `ConfluenceExporter`

Каталог `ConfluenceExporter/`, файл `ConfluenceExporter.csproj`, корневой namespace `ConfluenceExporter`. Имя читается в объявлениях (`ConfluenceExporter.CodeDocumentation.Analysis`) и прямо отражает назначение инструмента.

Рассмотренные альтернативы:

- `DotnetConfluenceExporter` — совпадает с именем репозитория и skill `dotnet-confluence-exporter`, но даёт избыточный префикс платформы `Dotnet` в корне namespace.
- `ConfluenceExporter.Cli` — подчёркивает консольный характер, но для единственного проекта решения создаёт лишний сегмент имени и расходится с именем каталога.
- `AppDocumentationExporter` — описывает результат работы, но не отражает целевое назначение (публикация в Confluence) и длиннее.
- `WebApp4.Docs` — отклонено: привязывает инструмент к конкретному приложению, хотя инструмент анализирует любое решение.

**Допущение:** имя `ConfluenceExporter` принято как основное. Конкретное имя не влияет ни на одно другое решение дизайна: при выборе иного имени меняются только значения в задачах (имя каталога, файла проекта, корневой сегмент namespace).

### 2. `RootNamespace` и `AssemblyName` не задаются явно

Свойства остаются неявными: после переименования файла проекта они автоматически равны `ConfluenceExporter`. Альтернатива — явно прописать оба свойства в `csproj` — отклонена: это дублирование значения, которое и так совпадает с именем проекта, и лишний источник расхождений при следующем переименовании.

### 3. Перемещение файлов через `git mv`

Каталог и файл проекта перемещаются `git mv`, чтобы Git зафиксировал переименование, а не пару «удаление + добавление». Альтернатива — создать новый каталог, скопировать файлы и удалить старый — разрывает историю файлов. Перед перемещением каталоги `AppDocs/bin` и `AppDocs/obj` удаляются, чтобы в новый каталог не переехали устаревшие артефакты сборки.

### 4. Замена только корневого сегмента namespace

Заменяется исключительно первый сегмент `AppDocs` → `ConfluenceExporter` в объявлениях `namespace` и директивах `using`; все остальные сегменты (`ApiDocumentGenerator`, `CodeDocumentation`, `Models`, `Internal`, `Analysis`, `Renders`) и имена типов сохраняются. Ровно поэтому задача проверяет, что в `git diff` присутствуют только строки `namespace`/`using`. Альтернатива — заодно пересмотреть структуру пространств имён — выходит за рамки переименования, не даёт наблюдаемого эффекта и увеличивает объём проверки.

### 5. Идентификатор проекта в решении сохраняется

В `WebApp4.slnx` меняется только `Path`; `Id="b2fb251c-cfd5-4be4-8f48-b663c570c0ee"` остаётся прежним. Альтернатива — выдать новый GUID — создаёт шум в истории и расходится с локальными конфигурациями решения (`.vs`), сохранёнными для существующего проекта.

### 6. Обновление `README.md` в рамках изменения

README сейчас содержит только заголовок, поэтому в него добавляется краткое назначение инструмента и команды сборки и запуска. Это позволяет проверить, что имя проекта в документации совпадает с фактическим, и не требует отдельного изменения.

## Risks / Trade-offs

- [Сборочные каталоги `AppDocs/bin` и `AppDocs/obj` могут переехать вместе с каталогом и дать устаревшие артефакты] → удалить их до `git mv`, после переименования выполнить сборку заново.
- [Часть вхождений старого префикса может остаться незамеченной] → контрольный поиск по отслеживаемым файлам не должен возвращать результатов, а сборка решения должна проходить без ошибок.
- [Ссылка на проект в решении может остаться устаревшей] → после правки `WebApp4.slnx` выполнить сборку решения и проверить наличие собранной сборки `ConfluenceExporter.dll`.
- [Наблюдаемое поведение может измениться незаметно] → до переименования фиксируется вывод `dotnet run` (baseline), после переименования вывод сравнивается с ним.
- [Открытое в IDE решение держит старые пути] → перезагрузить решение после переименования; на сборку и запуск из командной строки это не влияет.
- [Гипотетические внешние потребители namespace инструмента] → проверено: `AppDocs` встречается только внутри самого проекта и в `WebApp4.slnx`, поэтому ломающих последствий нет.

## Migration Plan

1. Снять baseline вывода инструмента (`dotnet run --project AppDocs/AppDocs.csproj`) в файл вне репозитория.
2. Удалить каталоги `AppDocs/bin` и `AppDocs/obj`.
3. Переместить каталог и файл проекта: `git mv AppDocs ConfluenceExporter`, затем `git mv ConfluenceExporter/AppDocs.csproj ConfluenceExporter/ConfluenceExporter.csproj`.
4. Обновить путь проекта в `WebApp4.slnx`.
5. Заменить корневой сегмент `namespace` и `using` в 29 файлах `.cs`.
6. Обновить `README.md`.
7. Собрать решение, сравнить вывод инструмента с baseline, выполнить контрольный поиск старого имени.

Откат: изменение целиком находится в рабочей копии и одном коммите, миграции данных и внешних эффектов нет — достаточно вернуть файлы из Git.
